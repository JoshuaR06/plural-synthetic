PLURALBRIDGE — TERMINOLOGY DICTIONARY (abbreviated for this document)
---------------------------------------------------------------------

TERMS

Plural
A person or collective whose plural structure is represented by a Plural Map.

Plural Map
A Plural Map describes how a plural understands their world.

Object
An entity represented in a Plural Map, including a System, Group, Place, or Member.

Anchor
An object that provides context for operations. Systems, Groups, and Places are anchors.

Placement
A relationship recording where an object appears in a Plural Map, including its parent anchor and ordering. An object may have multiple placements.

Structural membership
A relationship expressing that a member belongs to an anchor.

Access membership
A relationship associating an Account with an object for access purposes.

Role
The function or authority associated with participation in a relationship.

Account
A sign-in identity that can access objects through access membership. An Account is not a System.

Focus
The currently active anchor used as an operational context. Focus does not grant access.

PLURAL MAP EXAMPLES
-------------------

These examples illustrate possible structures, not an exhaustive list of permitted configurations.
Indentation illustrates placement or structural membership; annotations show other relationships or statuses.
A member shown in multiple locations is the same member, not a duplicate.
“Groups” is a collection heading in these diagrams, not an additional object type.

1. Simple Single-System Plural Map
A person signs in and has one System.

Account
├── System: The Harbor
│   ├── Member: A
│   ├── Member: B
│   ├── Member: C
│   └── Groups
│       ├── Group: Dancers
│       │   ├── Member: B
│       │   └── Group: Ballet
│       │       └── Member: A
│       └── Group: Musicians
│           ├── Member: A
│           └── Member: C
├── Notes
└── Front history
This is the simple default: one Account, one System anchor, members and groups inside it, and one focused anchor context.

2. Multiple Top-Level Systems Plural Map
A person has more than one root-level System. Neither root owns the other.

Account
├── System: The Harbor
│   ├── Member: A
│   ├── Member: B
│   └── Groups
│       └── Group: Harbor Group
│           ├── Member: A
│           └── Member: B
├── System: The Observatory
│   └── Member: C
├── Notes
└── Front history
This supports two distinct top-level Systems. Both are root anchors because neither is placed beneath another anchor.

3. Parent / Child Systems Plural Map
One System contains a smaller child System.

Account
├── System: Main House
│   ├── Member: Rowan
│   ├── Member: Tess
│   ├── Groups
│   │   └── Group: Main House Group
│   │       ├── Member: Rowan
│   │       └── Member: Tess
│   └── Child System: The Workshop
│       ├── Member: Kit
│       └── Member: Lark
├── Notes
└── Front history
The parent / child relationship describes structure. Access and privacy remain governed by access membership, roles, consent, and policy.

Encoding: The Workshop is the source of a systemRelationships record with relationshipType child and parentSystemId identifying Main House. targetSystemId is null. This canonical example encodes the child connection as a graph relationship; it does not add a placement for The Workshop or a reverse parent record. Access membership is separate and is not inherited through this relationship.

4. Sibling Systems Plural Map
Two Systems share a common relationship, but neither controls the other.

Account
├── System: Day Team (sibling)
│   ├── Member: A
│   ├── Member: B
│   └── Groups
│       └── Group: Day Team Group
│           ├── Member: A
│           └── Member: B
├── System: Night Team (sibling)
│   ├── Member: C
│   └── Member: D
├── Notes
└── Front history
This is useful for Systems that see themselves as parallel, cooperative, or operationally separate.

5. Related Systems Plural Map
Two Systems are related without a parent / child placement.

Account
├── System: The Archive (related)
│   └── Member: C
├── System: The Harbor (related)
│   ├── Member: A
│   ├── Member: B
│   └── Groups
│       └── Group: Harbor Group
│           ├── Member: A
│           └── Member: B
├── Notes
└── Front history
This could represent shared history, partial overlap, a past structure, or a loosely connected internal organization.

Encoding: related is a directed graph record (systemId -> targetSystemId). It is not parent/child and does not grant access. Both Systems are labeled (related) with no arrow, so encode two records: The Archive related -> The Harbor, and The Harbor related -> The Archive.

6. Subsystem / Nested Place Plural Map
An internal cluster may have its own structure within a System, without requiring another System.

Account
├── System: The Harbor
│   ├── Member: Alex
│   ├── Member: Morgan
│   ├── Member: Rae
│   ├── Groups
│   │   └── Group: Harbor Group
│   │       ├── Member: Alex
│   │       ├── Member: Morgan
│   │       └── Member: Rae
│   └── Place: Morgan's Room
│       ├── Member: M1
│       └── Member: M2
├── Notes
└── Front history

A nested Place represents an internal cluster without forcing its members into a flat list or a separate System.

Encoding: Harbor is the only System. Morgan's Room is a Place contained in Harbor (systemObjectPlacements, parent = Harbor). Alex, Morgan, and Rae are Harbor members and Harbor Group members. M1 and M2 belong to the Place (placeMemberships) and are not Harbor System members. The name "Morgan's Room" is a label. This example does not record a member-to-Place association and does not set associatedObjectId.

Model 6 uses the Place structure shown in its diagram. The permitted endpoints and associated-object semantics of the subsystem relationship remain a separate specification question.

7. Evolving / Uncertain Relationship Plural Map
The user knows two structures are connected, and the exact relationship is still forming.

Account
├── System: North Wing (evolving, unknown)
│   ├── Member: C
│   └── Member: D
├── System: The Harbor
│   ├── Member: A
│   ├── Member: B
│   └── Groups
│       └── Group: Harbor Group
│           ├── Member: A
│           └── Member: B
├── Notes
└── Front history
This gives the user a way to preserve reality-in-progress without prematurely naming it.

Encoding: North Wing and The Harbor are both root Systems. Encode one directed graph record: relationshipType evolving, systemId = North Wing, targetSystemId = The Harbor, relationshipStatus unknown. Do not name the connection as parent, child, sibling, related, subsystem, or ownership. unknown is the status of that evolving record, not a separate relationship type.

8. Archived System Plural Map
A System or structure still matters historically, but is no longer active.

Account
├── System: Current System
│   ├── Member: A
│   ├── Member: B
│   └── Groups
│       └── Group: Current Group
│           ├── Member: A
│           └── Member: B
├── System: Old Map (archived)
│   ├── Member: Archive A
│   ├── Member: Archive B
│   └── Groups
│       └── Group: Old Map Group
│           ├── Member: Archive A
│           └── Member: Archive B
├── Notes
└── Front history
This helps preserve migration meaning, old fronting records, old notes, and past organization.

Encoding: Old Map is a root System that is no longer active. Encode lifecycle on that System: status archived, isArchived true. Current System remains status active, isArchived false. Both Systems remain relationshipType root. This example does not include a predecessor or other graph edge between Old Map and Current System.

Historical meaning is preserved by retaining Old Map and its existing members, groups, notes, front history, and associations. Archiving the System does not automatically change the lifecycle state of those associated objects. Per-object archive flags on those associated records are independent facts, not an automatic cascade.

9. Non-Tree / Graph Plural Map
Some Systems may have overlapping or cross-linked relationships.

Account
├── System: A (related->B)
│   ├── Member: A1
│   ├── Member: A2
│   └── Groups
│       └── Group: A Group
│           ├── Member: A1
│           └── Member: A2
├── System: B (sibling->C)
│   └── Member: B1
├── System: C (associated->A)
│   └── Member: C1
├── Notes
└── Front history
Relationship examples:

A --related--> B
B --sibling--> C
C --associated--> A
This breaks the ordinary tree assumption. The structure becomes a graph of relationships instead of a single trunk with branches.

Encoding: encode exactly the three directed edges drawn here, plus a root record for each System: A related -> B, B sibling -> C, C associated -> A. Do not add B related -> A, C sibling -> B, or A associated -> C. Reciprocal records are used only where a diagram labels both sides with no arrow.

11. Place Collection of Systems Plural Map
A top-level Place contains two Systems, one of which contains another Place.

Account
├── Place: Central Hub
│   ├── System: The Harbor
│   │   ├── Member: Popeye

12. Non-System Anchors Plural Map
A top-level Place contains Group and Place anchors, with no Systems anywhere in the structure.

Account
├── Place: Central Hub
│   ├── Group: The Harbor
│   │   ├── Member: Popeye
│   │   └── Member: Gilligan
│   └── Group: Main House
│       └── Place: Waiting Room

├── Notes
└── Front history
Members can be organized through Groups and Places without requiring a System.

DESIGN RULES
------------

These examples illustrate the following PluralBridge design rules, grouped by subject.

1. Objects and Anchors
- Object identity consists of object type + object ID.
- Operations such as adding members require an anchor.
- A root anchor has no parent anchor in its root placement; a Plural Map may have multiple root anchors.
- An internal cluster can be represented using an appropriate anchor; it need not be a separate System.
- Archived is an object status, not a relationship type.

2. Placement, Membership, and Relationships
- Placement records where an object appears; structural membership records where a member belongs.
- An object may have multiple placements, and a member may belong to multiple anchors, without creating duplicate objects.
- Parent / child placements describe containment. Sibling, related, associated, and evolving / uncertain relationships describe other connections.
- Relationship arrows indicate direction. For these canonical examples, two Systems labeled with the same peer relationship and no arrow use two reciprocal directed records; a single arrow uses one directed record.

3. Access, Authority, and Auditing
- Access membership, roles, explicit permissions, consent, and policy govern access.
- Placement, structural membership, and descriptive relationships do not themselves grant access, authority, or visibility.
- Audit policy governs recording of activity.

4. Focus and Fronting
- Focus selects the active anchor context without creating access.
- Fronting is modeled within the focused anchor context.

5. Flexibility and Professional Use
- The default user experience can remain simple while the underlying model supports varied structures, including those with no Systems.
- Therapist-facing views should be user-controlled and privacy-aware.
- Professional input can improve safety without overriding lived experience.


CANONICAL JSON ENCODING
-----------------------

These field-level conventions describe the serialized canonical examples. They preserve the established encoding of Examples 1–11 while Example 12 demonstrates anchors with no Systems.

Encoding convention for these canonical examples

Graph records are directed. systemId is the source. Named peer associations use targetSystemId. Parent/child uses parentSystemId on the child record (relationshipType child).

When a diagram labels two Systems with the same peer type and draws no arrow, encode two directed records, one in each direction. When a diagram draws a single arrow (X --type--> Y), encode one directed record.

relationshipStatus is a state of a graph record. For Model 7 the established status token is unknown.

Archived is a System lifecycle state (status archived, isArchived true), not a graph relationship type. Model 8 does not include a predecessor edge.

Containment uses placements. Member-in-group and member-in-place use membership collections. Access uses memberships. None of these is implied by a graph relationship.

A root record in systemRelationships identifies a System with no parent System relationship. Its parentSystemId and targetSystemId are null. This serialized root marker is separate from a root anchor placement: in Examples 10 and 11, Systems retain root records while being placed beneath a Group or Place.

relationshipStatus remains optional. Model 7 uses unknown; broader use of statuses across relationship types is deferred. No additional tables, catalogs, or type/status rules are introduced.

Model 6 retains its Place encoding. The permitted endpoints and associated-object semantics of subsystem remain deferred.
